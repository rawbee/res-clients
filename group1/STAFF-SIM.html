Inside the Store Agent

How the system in the pitch actually works, traced one Cycle at a time — for the people who have to build it. Everything the Operator sees in the console has a mechanism behind it; this is the mechanism.

The one-sentence version

One Store Agent per dealership reads its Store's Signals and Guardrails, decides, and proposes Actions; every Action passes through one Execution Gateway that classifies it Auto / Review / Never in code, writes the Decision Ledger, and either mutates Google Ads, raises an Exception to the Operator, or refuses; Outcomes from the CDP flow back over each Action's Evaluation Window into Store Memory and the Portfolio Agent's calibration. That loop, 147 times a day.

1 · TRIGGER · scheduler

The daily Cycle fires

Google Ads' previous-day data settles overnight; the workflow runner starts one Cycle per Store around 05:30 local. This one is a daily Cycle, so it does a full review. (An intraday Cycle would only pace and look for anomalies; an event Cycle would be scoped to the Signal that fired it.)

Nothing has called a model yet. The runner is deterministic and durable — if the process dies mid-Cycle it resumes at the last completed step, and re-running a step never double-executes an Action (idempotency keys, §V).

A Cycle is a workflow, not a chat. The model is invoked at specific steps with a bounded packet, and every step's output is persisted before the next begins.

# cycle envelope
cycle_id:      cyc_2026-08-18_bct_daily
store:         st_0417  Bayou City Toyota · Houston TX
kind:          daily          # daily | intraday | event
trigger:       schedule 05:30 America/Chicago
data_asof:     2026-08-17 (Google Ads day complete)
idempotency:   st_0417:2026-08-18:daily
steps:         [assemble, observe, specialists, decide, gateway, ledger]
2 · ASSEMBLE · Signal ingestion → context packet

The Store Agent gets its packet

Ingestion has already normalized the sources into per-Store deltas. The packet is what the agent sees: Objectives, the applicable Guardrails after inheritance, yesterday's campaign state, the Signal deltas, and Store Memory excerpts retrieved because they resemble today's situation.

Two deltas jump out: new Tacoma inventory has fallen from 31 to 4 units, and aged used inventory (≥ 60 days) has risen from 29 to 47. Google Ads cannot see either.

The Guardrails block is resolved — enterprise defaults, brand overrides and Store overrides already merged — so the agent reasons about one set of numbers. The Gateway re-resolves independently at execution time; the agent's copy is for reasoning only.

3 · SPECIALISTS · shared skills, invoked by the Store Agent

Each Specialist proposes; none decides

The Store Agent invokes the Specialists relevant to a daily Cycle. Each returns candidate Actions with evidence and an expected effect. They are skills with narrow prompts and deterministic helpers (a search-term sweep is mostly a query, not a conversation), not agents with their own agenda — see ADR 0001.

Pacing and Search Terms return routine housekeeping. Structure returns nothing this Cycle. The interesting proposal is Pacing's reallocation, which the Store Agent will weigh against Store Memory.

Specialists are where most tuning will live: their thresholds are the parameters the Portfolio Agent calibrates (§IV).

4 · DECIDE · Store Agent

The agent decides and writes its reasoning

The Store Agent accepts the routine proposals and adopts the reallocation, citing the May 12 memory as precedent and setting its own reversal condition. It emits a list of Actions, each with the reasoning that will appear verbatim in the Ledger and on the Operator's Exception card.

Note what the agent does not do: it does not classify its own Actions as Auto or Review, and it does not touch Google Ads. It proposes.

The reasoning field is the product. If it is vague, the Operator will not trust the Auto tier and the Exception queue becomes the bottleneck the pitch says it is not.

5 · GATEWAY · tier check, in code

The Execution Gateway classifies each Action

The Gateway re-resolves the Guardrails for this Store and runs each Action through the classifier. It is a rules engine, not a model: type → applicable rule → magnitude → tier. Negatives and asset swaps are Auto. The budget shift is 14% of the source campaign's daily budget; the Auto ceiling is 10%; the shift is inside the monthly cap and touches no locked or Co-op Campaign, so it is Review, not Never.

Auto Actions are executed now, in a single idempotent batch, and confirmed against the API response. The Review Action is queued as an Exception. Everything — including what was refused — is written to the Ledger before any external call. See ADR 0002.

# gateway verdicts
a1 add_negative    rule: negatives.auto                → AUTO   executed
a2 add_negative    rule: negatives.auto                → AUTO   executed
a3 swap_asset      rule: creative.template_ok          → AUTO   executed
a4 shift_budget    rule: budget_shift_auto_max_pct
                   magnitude 0.14 > limit 0.10
                   monthly_cap ok · locked no · coop no
                                                       → REVIEW
                   queued as Exception exc_88213

# mutate batch (Auto only)

response          3/3 ok · partial_failure none · quota used 3
6 · LEDGER · the record

The Ledger entry, as written

One row per Action, plus one for the Cycle. The Operator's console is a view over this table; the learn step is a query over it. Because the entry carries the reasoning, the packet hash, and the evaluation window, a decision can be replayed later — which is how we intend to evaluate agent behavior offline before widening the Auto tier (§VII).

The Ledger is append-only. A rollback is a new Action that references the one it reverses, never an edit.

7 · OPERATOR · 07:12 CT, the Exception queue

Ask, then Approve

The Operator opens exc_88213 in the console, sees the reasoning and evidence, and Asks: “Why not wait for the shipment?” The Ask is routed back to the Store Agent with the Exception's packet as context; the reply is short and specific. The Operator approves. The Gateway executes a4 now — same batch path, same idempotency, tier recorded as REVIEW · approved by operator.

Modify is the same path with a changed magnitude; Reject writes a refusal to the Ledger and the agent's stated reminder condition becomes a watch.

# ask / reply
operator: Why not wait for the shipment?
store_agent: ETA is unconfirmed (3+ weeks per feed). Every day of
  Tacoma spend at 4 units is ~$300 of impressions on unavailable
  inventory. I'll propose reversing when inventory > 12.

8 · OUTCOME · 14 days later

The Evaluation Window closes

On Sept 1 the window for a4 closes. The Evaluation Window job joins CDP Outcomes for the Store to the Action's period and campaigns, computes the deltas against the pre-period, and writes them back to the Ledger row. That row becomes a Store Memory entry the next time a similar situation appears, and one more data point in the Portfolio Agent's calibration of the budget-shift threshold.

This is the whole “learn” mechanism: a measured Outcome attached to a decision, retrieved as context later. No retraining — ADR 0003.

# outcome write-back (a4)
window:        2026-08-18 → 2026-09-01
used_leads:    +19%  vs prior 14d     used_cpl: $41 → $40
new_leads:     −7%
aged_60d_sold: 5                      aged_60d_units: 47 → 39
cost_per_sold_unit (used): $304  (objective ≤ 310)
verdict:       consistent with expectation (+15–25%)
memory:        appended as mem_2026-08-18_shift_new_used
calibration:   datapoint → budget_shift threshold review (Toyota)
III · CVSTOSthe guardrail that acts on its own

Circuit Breaker mechanics

A Circuit Breaker is a performance Guardrail with a hand on the switch. It watches a leading indicator over a short window against a longer baseline; when it trips it freezes the Auto tier for that Store, rolls back the most plausible cause, and raises an Exception. It runs inside intraday Cycles and is deterministic — no model call to decide whether to trip.

Detect3-day mean of CPL vs 14-day baseline; trip if +35% (enterprise default) and volume is significant
FreezeAuto tier suspended for the Store; intraday pacing continues read-only
Roll backmost recent Action in scope that could plausibly move the indicator (here: a tCPA change)
RaiseException with the trace, hypotheses and a proposed way back to normal
Resumeonly by Operator decision; Portfolio Agent watches for clusters
Sooner Ridge Honda · Oklahoma City · Aug 3–16
TRIPPED +39.5%
  1. Freeze Auto tier for Sooner Ridge Honda
  2. Roll back tCPA $46 → $40 (Aug 13 Action, in scope)
  3. Raise Exception with hypotheses: Smart Bidding relearning after the target move; competitor “0% APR CR-V” event — “cr-v 0% apr” queries +180%
  4. Proposal on the card: resume Auto, tCPA $42, watch 7 days; watch-list competitor terms rather than negating them

What is in scope for rollback

  • Actions on this Store within the detection window that touch the tripped indicator's campaigns: target moves, budget shifts, structural changes.
  • Never negatives or asset swaps by default — low blast radius, and reverting them can reintroduce waste. They are listed on the Exception for the Operator.
  • Rollback is itself an Action through the Gateway: idempotent, Ledgered, reversible.

Why the breaker is dumb on purpose

  • It must fire even if the model is down, slow, or wrong. It is a query and a threshold.
  • The explanation is where the model helps: the Store Agent writes the hypotheses and the way back, and that is what the Operator reads.
  • Volume gate: no trip on tiny denominators (a Store with 6 leads a day will swing 40% on noise). Minimum-volume rules are part of the Guardrail.
IV · PORTFOLIVMthe one agent that sees across Stores

The Portfolio Agent

Store Agents cannot see each other. The Portfolio Agent reads the Ledger across all 147 Stores on a weekly Cycle (and immediately on Circuit Breaker clusters) and does three things: reallocate budget between Stores within corporate limits, calibrate the thresholds the Specialists and the Gateway use, and design Experiments so that “learn” is measured against a control.

Weekly reallocation

$18,400/ week

Moved from 9 Stores pacing under plan with soft demand (New Mexico, Kansas, Mississippi) to 12 Stores in DFW and Houston with aged used inventory rising.

Corporate limits: no Store below 85% of its envelope, none above 110%. Cross-Store moves are always Review — the Operator approves the packet as a whole.

Threshold calibration

10% → 15%Toyota · Auto budget shift

In 30 days the 23 Toyota Stores raised 38 Exceptions for shifts of 10–15%; 38 of 38 approved, median 4h 12m in queue. The Portfolio Agent proposes raising the Auto ceiling at brand scope.

Projected Toyota Exceptions per week: 11 → 4. The Operator moves the slider; the Gateway reads the new value on its next resolve. This is how autonomy grows: by evidence, one scope at a time.

Experiment readout

+9.4%used sold units vs holdout

12 weeks, 24-Store holdout, aged-inventory prioritization tactic on the rest. Cost per sold unit −11% versus the holdout.

Recommendation on the card: make aged-inventory priority an enterprise default Objective. The Operator decides; the Ledger records the Experiment as the reason.

How a holdout is chosen

  • Stratify Stores by brand, market and monthly budget; pick the holdout so each stratum is represented (24 of 147 ≈ 16%).
  • Holdout Stores keep running the agent, with the tactic under test disabled — they are not “unmanaged”, or the comparison measures the agent, not the tactic.
  • Pre-register the metric (used sold units, cost per sold unit), the window (12 weeks) and the minimum detectable effect before starting; the readout is computed by a fixed job, not by the model.
  • Guardrails still apply inside the Experiment. No Store is exposed beyond its envelope to make a test significant.
  • Seasonality is handled by the control, not by modeling; that is the point of holding out.
  • Results write to the Ledger and become Portfolio-level memory: “this tactic was measured, here is the effect, here is when.”
V · TVTELAthe boring parts that make autonomy acceptable

Safety engineering

The pitch's credibility rests on this section more than on the model. Each item below is a Gateway or workflow concern, implemented once, and none of them depend on a prompt behaving.

The Never list is code

Exceeding a monthly cap, editing conversion tracking, touching locked or Co-op Campaigns: rules in configuration the Gateway evaluates. The model can propose anything; the Gateway refuses and Ledgers the refusal. Prompts describe intent; they are never the safety mechanism.

Credentials never reach the model

The Store Agent has no Google Ads token. It emits Actions as data; only the Gateway holds credentials, and it holds them per customer account with the narrowest scope Google allows.

Idempotent mutations

Every Action carries an idempotency key (Store · Cycle · Action). A retried step or a duplicate event cannot double-shift a budget. The Ledger row is written before the API call and finalized after.

Rollback is first-class

Every mutating Action records enough to reverse it (previous budget, previous target, removed negative). Rollback is a new Action through the same Gateway — Ledgered and reversible again.

Dry-run mode

Per Store, per scope, or global: the Gateway classifies, Ledgers and returns as if executed, without mutating. This is the shadow mode of any rollout and the mode for offline evaluation.

Quotas and rate limits

Google Ads API operations are budgeted per Cycle and batched; the Gateway backs off on rate errors and defers non-urgent Auto Actions rather than dropping them. Test accounts for anything structural before it runs against a live customer.

Blast-radius bounds

Beyond per-Action Guardrails: a per-Store per-day cap on total budget moved, and a portfolio-level cap on Actions per hour. A misbehaving Specialist cannot rewrite 147 Stores before anyone notices.

Everything is replayable

Packets are hashed and stored; decisions can be re-run against history with a newer prompt or threshold to see what would have changed. This is how we earn each widening of the Auto tier.

Cost-of-thinking sanity check estimate

Order-of-magnitude model calls per day, at 147 Stores:

  • Daily Cycles: 147 × ~8 calls (assemble/decide plus Specialist calls that need a model; several Specialists are mostly queries) ≈ 1,200
  • Intraday checks: 4 × 147 = 588 runs, deterministic unless an anomaly needs explaining; ~10% escalate to a model call ≈ 60
  • Event Cycles: ~50 Signals/day across the portfolio × ~3 calls ≈ 150
  • Asks, Portfolio, Experiments: tens, not hundreds

≈ 1,400–1,600 model calls a day, each carrying a bounded packet — call it 30–60K tokens in, a few K out — so roughly 50–90M input tokens/day before caching. Packets share large stable prefixes (Objectives, resolved Guardrails, campaign structure), which is what prompt caching exists for; expect the effective number to be well under that.

This is a design-stage estimate to show the shape is affordable relative to a $4.6M/month media budget, not a quote. Price it properly against the current rate card when the stack is decided.

VII · PERICVLAwhat could make this hard — internal, candid

Open questions and build risks

None of these are reasons not to build. They are the places where the estimate is most likely to be wrong and where the first design spikes should go.

  • high
    Attribution latency

    Sold units land days to weeks after the click; Evaluation Windows of 14–28 days mean the learn loop is slow by construction. Mitigation: steer on leading indicators daily, reconcile to sales on window close (D11); accept that calibration is a monthly rhythm, not a daily one.

  • high
    CDP data quality and Store-level identity

    Outcomes are only as good as the CDP's join from lead to sale to Store. Cross-Store shoppers, duplicate leads and DMS timing will make store-level Outcomes noisy. Mitigation: identity resolution is an ingestion concern with its own tests; minimum-volume gates on any threshold that reads Outcomes; expect a data-quality discovery phase before Auto widens.

  • high
    Trusting Auto before it has earned it

    The pitch's operating model only works if the Operator lets ~96% of Actions run unreviewed. That trust has to be earned per Action type. Mitigation: dry-run everything first; offline replay against history; widen the Auto tier by evidence (the §IV calibration story), never by fiat.

  • medium
    Exception fatigue

    31 Exceptions a day is fine; 300 is a queue nobody reads and an Auto tier by neglect. Mitigation: Exception volume is itself a metric the Portfolio Agent watches; batching similar Exceptions; the “make this Auto going forward” affordance is the pressure valve.

  • medium
    Smart Bidding relearning

    Every target move perturbs Google's own model; too many small moves keep it in permanent relearning, which looks like a breaker trip. Mitigation: minimum dwell time between target moves per campaign, encoded as a Guardrail; the Sooner Ridge case is the canonical example.

  • medium
    PMax opacity

    Performance Max exposes little that an agent can act on beyond budgets, asset groups, and some signals; the Specialist toolkit shrinks there. Mitigation: be explicit about which Specialists apply per campaign type; treat PMax as budget-and-assets territory.

  • medium
    Co-op compliance

    OEM-funded campaigns carry copy, keyword and reporting rules; a wrong Auto Action can cost reimbursement. Mitigation: Co-op Campaigns Review or locked by default (D2); the compliance rulebook is a Guardrail set per brand, ideally supplied by Group 1's OEM relationships.

  • medium
    Google API and policy drift

    Google Ads API versions sunset roughly yearly; features move; policies change what an automation may do. Mitigation: the Gateway isolates the surface; version upgrades are a Gateway concern; monitor Google's automation policy for third-party tools.

  • low
    Model cost per Cycle

    The §VI estimate is comfortable against the media budget, but a chatty Specialist design could multiply it. Mitigation: Specialists that are queries stay queries; cache stable packet prefixes; measure tokens per Cycle from day one.

  • low
    Operator adoption

    The console replaces agency status calls with a queue and a Ledger. If the reasoning fields are weak, the Operator will route around the system. Mitigation: reasoning quality is a first-class evaluation target; the Ask path exists to keep humans in dialogue rather than in approval mode.

ADR 0001 · Two-level topology

One Store Agent per Store, one Portfolio Agent, Specialists as skills. Rejected: per-function agents (no store context), 147 monoliths (no portfolio layer), Specialists as sub-agents (conflicting agendas, no single owner).

ADR 0002 · Single Execution Gateway

All mutations through one path; tier and Never enforced in code; Ledger always; CDP and DMS read-only. Prompts are never the safety mechanism.

ADR 0003 · Learning without retraining

Store Memory + calibrated thresholds + designed Experiments. Retraining rejected: opaque, slow, unauditable — and not the bottleneck.
